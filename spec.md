# Specification: Tracker

## 1. Модель места

Каждое место MUST содержать следующие поля:

| Поле | Тип | Описание |
|---|---|---|
| id | string | Уникальный идентификатор |
| title | string | Название места |
| address | string | Адрес |
| latitude | number | Широта |
| longitude | number | Долгота |
| category | string | Категория |
| comment | string | Комментарий |
| status | string | Статус места |
| createdAt | datetime | Дата создания |
| visitedAt | datetime/null | Дата посещения |
| photos | array | Фотографии |
| review | string | Впечатления о посещении |
| rating | integer/null | Оценка от 1 до 5 |
| sortOrder | number | Порядок отображения |

Допустимые статусы:
- `wishlist` — хочу посетить.
- `visited` — посещено.

Оценка MUST быть целым числом от 1 до 5 либо отсутствовать.

Название MUST содержать хотя бы один символ после применения trim.

## 2. Категории

Приложение MUST предоставлять следующие категории по умолчанию:

- Кафе и рестораны
- Парки
- Музеи
- Развлечения
- Другое

Пользователь MUST иметь возможность создавать собственные категории.

Категории MUST быть доступны при добавлении и редактировании места.

Фильтрация по категориям MUST изменять только отображение, но не исходные данные.

## 3. Интерактивная карта

### Requirements

- Карта MUST быть основным экраном приложения.
- Картографическая подложка MUST использовать OpenStreetMap.
- Начальный центр карты MUST соответствовать Москве.
- Карта MUST поддерживать перемещение и изменение масштаба.
- Управление MUST работать мышью и сенсорными касаниями.
- Все места с корректными координатами MUST отображаться маркерами.
- Маркеры MUST визуально различать статусы wishlist и visited.
- При большом количестве маркеров MUST использовать кластеризацию.
- Карта MUST показывать название и краткую информацию о месте при нажатии на маркер.
- MUST поддерживаться добавление места через выбор точки на карте.
- При выборе точки координаты MUST сохраняться автоматически.
- MUST поддерживаться перемещение маркера при редактировании координат.
- MUST отображаться атрибуция © OpenStreetMap contributors.

### Scenarios

#### Сценарий: Запуск карты

WHEN пользователь запускает приложение
THEN отображается интерактивная карта Москвы
AND на карте присутствуют маркеры сохранённых мест.

#### Сценарий: Изменение области карты

WHEN пользователь перемещает карту или меняет масштаб
THEN карта корректно отображает соответствующую географическую область.

#### Сценарий: Добавление места через карту

WHEN пользователь выбирает точку на карте
THEN координаты выбранной точки автоматически записываются в форму
AND после сохранения появляется новый маркер.

#### Сценарий: Просмотр информации о месте

WHEN пользователь нажимает на маркер
THEN открывается краткая информация о соответствующем месте.

#### Сценарий: Недоступность карты

WHEN картографические тайлы недоступны
THEN приложение показывает понятное сообщение о недоступности карты
AND каталог и сохранённые данные остаются доступными.

## 4. Режим карточек

### Requirements

Приложение MUST предоставлять отдельный режим просмотра карточек.

MUST поддерживаться три списка:
- Все места.
- Хочу посетить.
- Посетили.

Каждая карточка MUST отображать:
- Фотографию или заглушку.
- Название.
- Категорию.
- Адрес.
- Статус.

MUST присутствовать поиск и фильтры.

Оба режима MUST использовать один источник данных.

### Scenarios

#### Сценарий: Переключение режимов

WHEN пользователь переключает режим «Карта» / «Карточки»
THEN данные мест остаются одинаковыми
AND изменения в одном режиме отражаются в другом.

#### Сценарий: Фильтрация

WHEN пользователь выбирает список «Хочу посетить»
THEN отображаются только места со статусом wishlist
AND общая статистика не изменяется.

## 5. Управление местами

### Requirements

Приложение MUST поддерживать:
- Добавление места через форму.
- Добавление места через выбор точки на карте.
- Редактирование существующего места.
- Удаление места.

Все операции MUST изменять единый набор данных.

Название после trim MUST быть непустым.

При редактировании MUST сохраняться идентификатор места.

### Scenarios

#### Сценарий: Добавление места

WHEN пользователь заполняет корректную форму и сохраняет место
THEN новое место появляется в каталоге и на карте.

#### Сценарий: Редактирование места

WHEN пользователь изменяет данные существующего места
THEN изменения сохраняются во всех режимах отображения.

#### Сценарий: Удаление места

WHEN пользователь удаляет место
THEN оно исчезает из каталога и с карты
AND статистика пересчитывается.

## 6. Drag & Drop

### Requirements

- Карточки MUST поддерживать перетаскивание внутри списков.
- Карточки MUST поддерживать перенос между wishlist и visited.
- При переносе между списками статус MUST изменяться автоматически.
- Изменённый порядок MUST сохраняться.
- MUST отображаться визуальная подсветка предполагаемого места вставки.
- Перемещение MUST сопровождаться плавной анимацией.
- MUST поддерживаться автоматическая прокрутка при приближении к границам контейнера.
- MUST поддерживаться сенсорное управление.
- Перетаскивание MUST не конфликтовать с обычным нажатием на карточку.
- MUST существовать альтернативное управление порядком и статусом без Drag & Drop.

### Scenarios

#### Сценарий: Перенос между списками

WHEN карточка перемещается из wishlist в visited
THEN статус места изменяется на visited
AND обновляются счётчики
AND изменение сохраняется.

WHEN карточка перемещается из visited в wishlist
THEN статус места изменяется на wishlist
AND обновляются счётчики
AND изменение сохраняется.

#### Сценарий: Перемещение внутри списка

WHEN пользователь меняет положение карточки внутри списка
THEN новый порядок сохраняется после завершения перемещения.

## 7. Информация о посещении

### Requirements

Для посещённого места MUST поддерживаться:
- Дата посещения.
- Загрузка нескольких фотографий.
- Удаление фотографий.
- Текстовый отзыв или впечатления.
- Оценка от 1 до 5 звёзд.

Все поля MUST быть доступны для последующего редактирования.

### Scenarios

#### Сценарий: Сохранение воспоминаний

WHEN пользователь добавляет дату, фотографии, отзыв и оценку
THEN информация сохраняется вместе с местом
AND остаётся доступной после перезапуска приложения.

#### Сценарий: Редактирование фотографий

WHEN пользователь добавляет или удаляет фотографию
THEN изменения сохраняются локально.

## 8. Трекер приключений

### Requirements

Интерфейс MUST показывать три счётчика:

- Всего мест.
- Уже посетили.
- Пока в планах.

Прогресс MUST рассчитываться по формуле:

`round(100 * visitedCount / totalCount)`

При отсутствии мест прогресс MUST равняться 0%.

Счётчики MUST рассчитываться по всему каталогу независимо от фильтров, поиска и активного режима.

### Scenarios

#### Сценарий: Обновление статистики

WHEN пользователь добавляет, удаляет или меняет статус места
THEN счётчики и прогресс автоматически пересчитываются.

#### Сценарий: Пустой каталог

WHEN все места удалены
THEN все счётчики равны 0
AND прогресс равен 0%
AND NaN или Infinity не отображаются.

#### Сценарий: Активный фильтр

WHEN пользователь включает фильтр «Хочу посетить»
THEN список отображает только запланированные места
AND общая статистика остаётся прежней.

## 9. Локальное хранение и резервное копирование

### Requirements

- Приложение MUST использовать IndexedDB.
- Данные мест и фотографии MUST храниться локально.
- После перезапуска приложения данные MUST восстанавливаться.
- MUST поддерживаться экспорт полной резервной копии.
- Резервная копия MUST включать фотографии и пользовательские категории.
- MUST поддерживаться импорт резервной копии.
- При ошибках хранилища MUST отображаться понятное сообщение.
- Приложение MUST предупреждать пользователя о риске потери несохранённых изменений.
- Импорт MUST проверять структуру резервной копии до изменения текущих данных.

### Scenarios

#### Сценарий: Восстановление данных

WHEN пользователь закрывает и повторно открывает приложение
THEN ранее сохранённые места и фотографии восстанавливаются.

#### Сценарий: Экспорт

WHEN пользователь запускает экспорт
THEN формируется полная резервная копия всех данных, включая фотографии.

#### Сценарий: Импорт

WHEN пользователь импортирует корректную резервную копию
THEN данные восстанавливаются в приложении.

#### Сценарий: Ошибка IndexedDB

WHEN приложение не может сохранить данные
THEN пользователь получает понятное уведомление
AND приложение не должно молча отбрасывать несохранённые изменения.

## 10. Адаптивность и дизайн

### Requirements

- Интерфейс MUST быть преимущественно розовым.
- MUST использовать мягкие оттенки и аккуратную типографику.
- Карточки MUST иметь единый визуальный стиль.
- MUST использовать плавные анимации и понятные иконки.
- Интерфейс MUST оставаться функциональным и не чрезмерно декоративным.
- Карта MUST занимать основное пространство экрана.
- Все кнопки и поля MUST иметь понятные подписи.
- MUST поддерживаться экраны шириной от 390 px.
- MUST отсутствовать горизонтальная прокрутка на поддерживаемой ширине.

### Scenarios

#### Сценарий: Мобильный экран

WHEN приложение открывается на экране шириной 390 px
THEN все основные функции остаются доступными
AND горизонтальная прокрутка отсутствует.

## 11. Начальные данные

Приложение MUST содержать несколько примеров реальных мест Москвы с корректными координатами.

Обязательные примеры:
- Парк «Зарядье» — wishlist.
- ГУМ — visited.

Начальный каталог MUST быть обозначен как демонстрационный пример, а не полный список мест Москвы.

## 12. Ограничения OpenStreetMap

- MUST использовать картографическую подложку OpenStreetMap.
- MUST отображать атрибуцию © OpenStreetMap contributors.
- MUST загружать тайлы через интернет.
- MUST NOT массово скачивать публичные тайлы для офлайн-использования.
- Недоступность тайлов MUST NOT блокировать каталог и локальные данные.
- MUST NOT имитировать синхронизацию между устройствами.
